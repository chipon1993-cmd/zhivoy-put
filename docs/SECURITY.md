## Реализованная граница доверия

Браузер отправляет email/пароль по HTTPS в `/api/auth`; Vercel проверяет их через
Supabase Auth. В ответе браузер получает только результат, а access token — в
cookie `__Host-zp_session` с `HttpOnly; Secure; SameSite=Strict; Path=/` без Domain.
Refresh token не сохраняется и не передаётся JavaScript. Срок cookie — максимум
один час, не больше срока access token; затем нужен повторный вход. Это намеренный
простой режим, без фонового refresh и связанных с ним гонок.

Каждый запрос административной страницы/ресурса, сохранения, чтения сообщений и
публикации проверяет пользователя онлайн через `/auth/v1/user`, затем текущую
запись `site_admins` через RLS. Авторизация не использует `user_metadata`, email-
список или `localStorage.isAdmin`. `user_metadata.name` используется только как
отображаемое имя с экранированием.

RLS проверяет также существование принадлежащей пользователю сессии в
`auth.sessions` по `session_id` проверенного JWT. Поэтому удаление членства или
выход (`logout?scope=local`) запрещают следующий административный запрос, даже
если срок старого JWT ещё не истёк. Уже выполняющийся запрос может закончиться;
это не механизм отмены транзакций или уже отправленного GitHub-коммита.

Для изменяющих запросов обязательны точный Origin из `APP_ORIGIN`, JSON и заголовок
`X-Requested-With: zhivoy-put`. Нет доверия `Host`, `X-Forwarded-Host`, присланным
ролям, путям или Authorization-заголовку клиента. Нет CORS-разрешения для других
сайтов. Ответы API/админки запрещают браузерный и CDN-кэш. Ошибки не возвращают
тела ответов провайдеров и секреты. Если Supabase или конфигурация недоступны,
привилегированные действия блокируются.

Публичные страницы и опубликованный JSON продолжают работать как статика.
`dist` создаётся по явному списку публичных каталогов; `admin`, `api`, `server`,
SQL, `.env` и зависимости туда не копируются. `/admin`, `/admin/index.html`,
`/admin/editor`, скрипты и стили панели обслуживаются защищённой Vercel Function.
Прямой `/api/admin?file=...` проходит ту же проверку. Защита не основана на rewrite
или скрытии ссылки: проверка находится внутри обработчика.

Сохранение в Supabase, как и раньше, означает **живое изменение CMS**, а не приватный
черновик. Публикация дополнительно записывает JSON в GitHub для статической версии
и запускает интеграцию Vercel, если она настроена. Это два отдельных сервиса:
успешное облачное сохранение и неудачный GitHub-коммит не откатывают друг друга.
При конфликте SHA API возвращает 409. Перед параллельным редактированием используйте
«Загрузить данные с GitHub»: этот путь запоминает SHA. Первый publish без pull
проверяет SHA только между серверным чтением и записью; это не полная система
версионирования черновиков.

## Что необходимо сделать во внешних службах

Не сливать изменение в production до завершения подготовки. В текущем состоянии
без внешних настроек новая админка будет закрыта — это ожидаемый безопасный отказ.
Сначала отдельный тестовый Supabase/окружение и проверка, затем согласованное
обновление production. Изменения ниже не выполнялись.

### Supabase

1. Возобновить/восстановить **нужный** проект у владельца. Сделать резервную копию.
   Не переносить данные другого проекта (например, «Орбиты») по совпадению владельца.
2. Прочитать реальную схему и все политики. Минимальные запросы без личных данных:

   ```sql
   select tablename, policyname, roles, cmd, qual, with_check
   from pg_policies where schemaname = 'public';
   select table_name, column_name, data_type
   from information_schema.columns
   where table_schema = 'public' and table_name in ('site_data','site_admins','contact_inbox');
   select c.relname, c.relrowsecurity from pg_class c
   join pg_namespace n on n.oid = c.relnamespace
   where n.nspname = 'public' and c.relkind = 'r';
   ```

3. Сверить типы `site_data.key/value/updated_at` и ограничения с `security.sql`.
   `CREATE TABLE IF NOT EXISTS` не исправляет несовместимую существующую схему.
   Скрипт заменяет **все** политики на трёх перечисленных таблицах; проверить,
   что другие приложения не зависят от них. Запустить транзакцию сначала на копии.
   Убедиться, что схема `private` не входит в exposed schemas Data API, а владельцем
   `private.is_site_admin()` является административная роль, не клиентская.
4. Проверить число перенесённых сообщений. Для идемпотентности используется
   детерминированный ID содержимого; одинаковые сообщения могут объединиться.
   Даты переноса заменяют старые даты, исходный JSON сохраняет оригинал.
   Сообщения с невалидными/слишком длинными полями остаются в закрытом исходнике
   для ручного разбора. Общий `navigator_data` **не мигрируется**: владельца
   восстановить из прежней структуры нельзя. Навигатор продолжает работать
   локально; общая облачная синхронизация отключена до отдельной модели `user_id`.
5. В Auth включить email/password, обязательное подтверждение email, задать Site
   URL равным `APP_ORIGIN` и точные разрешённые redirect URL без wildcard.
   Настроить SMTP, политику паролей и rate limits. Формы для MFA, восстановления
   пароля и смены email в эту версию не входят; администратору нужен отдельный
   следующий этап MFA с серверным требованием `aal2`, не только переключатель UI.
6. Для Confirm signup использовать ссылку (значения секрета здесь нет):

   ```html
   <a href="{{ .SiteURL }}/pages/confirm.html?token_hash={{ .TokenHash }}">Подтвердить email</a>
   ```

   Страница убирает одноразовый hash из адресной строки и требует нажатия кнопки,
   поэтому простое сканирование ссылки почтовиком не расходует код. API допускает
   только подтверждение signup, не recovery/invite/magiclink. Не использовать
   стандартный implicit callback, который возвращает session tokens в fragment.
   Проверить, позволяет ли тариф менять шаблон; может потребоваться custom SMTP.
7. Создать собственную учётную запись через Supabase Auth, подтвердить email,
   выбрать её UUID в Dashboard. Только оператор БД назначает роль:

   ```sql
   insert into public.site_admins(user_id) values ('<verified-auth-user-uuid>');
   ```

   Не переносить роли/хеши из localStorage и не делать «первого зарегистрированного»
   администратором. Для отзыва удалить строку из `site_admins`, затем отозвать
   сессии через Auth. Проверить Supabase security advisors и выполнить матрицу ниже.

- Задать переменные в Dashboard; реальные значения не отправлять в чат и не
  коммитить. Все читаются сервером, без `NEXT_PUBLIC_`/`VITE_`:

  |---|---|
  | `APP_ORIGIN` | Один точный HTTPS origin без завершающего `/`; production и preview имеют разные значения. |
  | `SUPABASE_URL` | URL нужного проекта. |
  | `SUPABASE_PUBLISHABLE_KEY` | Publishable key этого проекта. Не service_role. |

  запрещает GitHub-запись при `VERCEL_ENV != production`; тест реальной записи

  отдельными данными, не с production токеном в PR-preview.
- Включить Deployment Protection для preview и старых deployment URL; проверить
  bypass-ссылки и исключения. Это дополнительная защита deployment, а не замена

## Проверка и границы результата

Локально: `npm ci --ignore-scripts`, `npm test`, `npm run build`.
Тесты используют фиктивные credentials и mocked HTTP провайдеров; SQL исполняется
в реальном движке PostgreSQL через PGlite с тестовыми таблицами `auth.users` и
`auth.sessions`. Это не проверка работающего Supabase Auth или production routing.
Дополнительно проверяются синтаксис скриптов и отсутствие закрытых файлов в dist.
Полный браузерный прогон не выполнен: Chromium отсутствовал, загрузка тестового
браузера в этой среде завершилась ошибкой. Приёмка ниже обязательна до включения.

| Проверка на тестовом deployment | Ожидаемый результат |
|---|---|
| Без cookie: `/admin`, `/admin/`, `/admin/index`, `/admin/index.html`, `/admin/editor.html` | Переход на вход, HTML панели не выдаётся. |
| Без cookie: `/api/admin?file=index.html`, `/admin/js/github-sync.js` | Та же серверная защита. |
| В localStorage записан `isAdmin: true` | Не влияет на доступ. |
| Cookie подделан/истёк, Supabase недоступен | Отказ; никаких fallback-admin. |
| Обычный подтверждённый пользователь обращается к CMS PUT, inbox, GitHub API | 403, запись/чтение не выполняются. |
| Тот же пользователь изменяет user_metadata на admin | Привилегии не появляются. |
| Прямой Supabase anon/authenticated запрос к чужим данным/ролям | RLS/grants не дают доступ; публичны только восемь CMS-ключей. |
| Подтверждённый назначенный администратор | Панель, редактор, сохранение, pull/history и разрешённый publish работают. |
| Удалить членство или выполнить logout, повторить запрос со старым cookie | Запрет следующей административной операции. |
| Запрос с чужого Origin, без custom header, text/plain, слишком большой JSON | 403 / 415 / 413, без изменения данных. |
| Попытка изменить repo/branch/path или записать `../js/auth.js` через builder | Фиксированная серверная цель / 400. |
| Публикация страницы с script, onerror, javascript-ссылкой | Исполняемые вставки удалены; системные страницы не перезаписаны. |
| Запись из preview | Заблокирована сервером. |
| Форма обратной связи | Сообщение добавлено без загрузки чужих сообщений; администратор видит и удаляет его. |
| Выход, затем offline/back | Нет нового авторизованного ответа, новый SW не кэширует админку/API. Старые вкладки не могут публиковать. |
| Проверка bundle/Network/storage | Нет PAT, refresh token, service_role или встроенного admin-пароля в клиенте; cookie недоступен document.cookie. |

Нужно проверить холодный старт функций, includeFiles, clean URLs, security headers,
подтверждение email и очистку старого service worker в настоящем браузере.
Сторонние CDN-скрипты панели остаются доверенным кодом: HttpOnly не мешает XSS
выполнять действия от имени вошедшего пользователя. DOMPurify закрывает найденные
вставки, но не заменяет полный XSS-аудит. Дальнейшее усиление: локальные bundles
проверенных CDN-зависимостей, SRI/строгий CSP с nonce, MFA, журнал публикаций с
результатами и изоляция админки на отдельном origin.

Безопасный rollback: отключить `GITHUB_PUBLISH_ENABLED`, закрыть панель внешней
защитой и восстановить публичные статические страницы. Не возвращать старые
открытые RLS и браузерные токены ради работоспособности панели. Уже отозванные
PAT не восстанавливать.
